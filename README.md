# BrifNet M-Pesa Gateway

WordPress plugin that provides an application-facing API for M-Pesa payments and webhook notifications.

The gateway handles:

* M-Pesa STK Push initiation
* Safaricom Daraja STK callbacks
* Safaricom Daraja C2B callbacks
* Payment persistence
* Payment completion events
* Webhook registration and delivery
* HMAC-SHA256 webhook signatures
* At-least-once webhook delivery
* Idempotent payment and webhook processing

---

## Requirements

* WordPress
* PHP 8.4+
* Composer
* M-Pesa/Daraja credentials
* Public HTTPS URL for webhook delivery

The plugin uses Composer dependencies.

---

# Installation

## 1. Clone or Download

Place the plugin in the WordPress plugins directory:

```text
wp-content/plugins/brifnet-mpesa-gateway
```

For example:

```text
wp-content/
└── plugins/
    └── brifnet-mpesa-gateway/
```

## 2. Install Dependencies

From the plugin directory:

```bash
composer install
```

This installs the dependencies from `composer.lock` and creates the `vendor/` directory.

The `vendor/` directory is generated by Composer and should not be committed.

## 3. Activate the Plugin

From WordPress:

```text
Plugins → Installed Plugins → BrifNet M-Pesa Gateway → Activate
```

The plugin registers its REST routes when WordPress loads the plugin.


```env
# M-Pesa / Daraja credentials
```

# Daraja Callback URLs

The plugin provides the WordPress REST endpoints used to receive callbacks from Safaricom Daraja.

These routes are created automatically when the plugin is loaded.

They are separate from the client-facing API.

For a site running at:

```text
https://example.com
```

the callback endpoints are:

## STK Callback

```text
https://example.com/wp-json/brifnet/v1/mpesa/callback
```

This receives the asynchronous result of an STK Push request.

Configure this URL as the callback URL used by the STK Push integration.

The URL is supplied through:

```env
DARAJA_CALLBACK_URL=https://example.com/wp-json/brifnet/v1/mpesa/callback
```

## C2B Callback

```text
https://example.com/wp-json/brifnet/v1/mpesa/c2b
```

This receives C2B validation and confirmation requests from Daraja.

Use this URL when configuring the corresponding C2B integration.

## Callback Registration

The plugin currently does not register these URLs with Safaricom automatically.

Daraja registration is currently a manual setup step.

Automatic registration may be added later.

## Callback Requirements

The WordPress site receiving Daraja callbacks must be publicly accessible.

For production:

* Use HTTPS.
* Do not require normal WordPress authentication on callback routes.
* Make sure Safaricom can reach the endpoints.
* Do not use `localhost` for Daraja callbacks.

The plugin throws a configuration error when a required environment variable is missing or empty.

# 1. Initiate an STK Push

```http
POST /wp-json/brifnet/v1/mpesa/stk
Content-Type: application/json
```

## Request

```json
{
  "reference": "PAY-CB-003",
  "phone": "0729633304",
  "amount": 349
}
```

## Fields

| Field       | Type    | Description                                          |
| ----------- | ------- | ---------------------------------------------------- |
| `reference` | string  | Payment reference supplied by the client application |
| `phone`     | string  | Customer's Kenyan phone number                       |
| `amount`    | integer | Amount to request from the customer                  |

The phone number must use the Kenyan local format:

```text
07XXXXXXXX
```

The amount must be greater than zero.

The `reference` belongs to the client application and is used to correlate the payment with its own business record.

## Successful Response

```http
200 OK
```

```json
{
  "message": "STK Push initiated.",
  "merchant_request_id": "3b8d-40c5-817d-9beb9d179fd433836",
  "checkout_request_id": "ws_CO_050920260057144729633304"
}
```

The `merchant_request_id` and `checkout_request_id` identify the STK request at the provider.

A successful STK Push response only means that the request was accepted for processing.

It does not mean that the customer has paid.

Payment completion is communicated through the `payment.completed` webhook.

## Possible Errors

### Invalid Request

```http
400 Bad Request
```

```json
{
  "message": "Invalid request."
}
```

### M-Pesa Rejected the Request

```http
502 Bad Gateway
```

```json
{
  "message": "M-Pesa rejected the STK Push.",
  "error": "..."
}
```

### Internal Error

```http
500 Internal Server Error
```

```json
{
  "message": "Unable to initiate payment."
}
```

# 2. Webhooks

Applications can register webhook endpoints to receive payment events.

The currently supported event is:

```text
payment.completed
```

## Register a Webhook

```http
POST /wp-json/brifnet/v1/webhooks
Content-Type: application/json
```

Request:

```json
{
  "url": "https://example.com/webhook",
  "events": [
    "payment.completed"
  ]
}
```

The `events` field is an array so an endpoint can subscribe to multiple events as more events are added.

## Response

```json
{
  "url": "https://example.com/webhook",
  "active": true,
  "events": [
    "payment.completed"
  ]
}
```

New webhook registrations are active immediately.

# 6. Payment Completed Webhook

When a payment is completed, the gateway creates a `payment.completed` event and sends it to every active webhook endpoint subscribed to that event.

Example request:

```http
POST https://example.com/webhook
Content-Type: application/json
X-Webhook-Signature: <signature>
```

The payload depends on the payment channel.

## STK Payment

```json
{
  "event_id": "evt-123",
  "event": "payment.completed",
  "occurred_at": "2026-09-04T12:30:00+03:00",
  "data": {
    "reference": "PAY-123",
    "phone": "0712345678",
    "amount": 500,
    "channel": "STK",
    "provider_reference": "ws_CO_67890",
    "provider_transaction_id": "ABC123XYZ"
  }
}
```

### STK Fields

| Field                          | Description                                          |
| ------------------------------ | ---------------------------------------------------- |
| `event_id`                     | Unique identifier for the payment event              |
| `event`                        | Event name                                           |
| `occurred_at`                  | Time the event occurred                              |
| `data.reference`               | Payment reference supplied by the client application |
| `data.phone`                   | Customer phone number                                |
| `data.amount`                  | Payment amount                                       |
| `data.channel`                 | Payment channel                                      |
| `data.provider_reference`      | M-Pesa STK request reference                         |
| `data.provider_transaction_id` | M-Pesa transaction/receipt identifier                |

The client application should use its own `reference` to correlate an STK payment with the payment request it originally created.

## C2B Payment

C2B payments work differently because there is no payment request created by the client application before the customer pays.

Example:

```json
{
  "event_id": "evt-456",
  "event": "payment.completed",
  "occurred_at": "2026-09-04T12:30:00+03:00",
  "data": {
    "account_number": "KAM100",
    "phone": "0712345678",
    "amount": 349,
    "channel": "C2B",
    "provider_transaction_id": "RKT123456"
  }
}
```

### C2B Fields

| Field                          | Description                                                 |
| ------------------------------ | ----------------------------------------------------------- |
| `event_id`                     | Unique identifier for the payment event                     |
| `event`                        | Event name                                                  |
| `occurred_at`                  | Time the event occurred                                     |
| `data.account_number`          | Account number supplied in the M-Pesa `BillRefNumber` field |
| `data.phone`                   | Customer phone number                                       |
| `data.amount`                  | Payment amount                                              |
| `data.channel`                 | Payment channel                                             |
| `data.provider_transaction_id` | M-Pesa `TransID`                                            |

For C2B payments:

```text
BillRefNumber → account_number
TransID       → provider_transaction_id
```

The gateway also creates its own internal payment reference for the C2B payment. That internal reference is used by the gateway and is not used as the client correlation field in the C2B webhook.

The provider transaction ID remains the idempotency key for the C2B payment.

# 7. Webhook Delivery

For `payment.completed`, the gateway creates a delivery record for each active endpoint subscribed to the event.

The delivery model is **at-least-once**.

```text
Payment Completed
       |
       v
Payment Event
       |
       v
Matching Active Webhooks
       |
       v
Delivery Record
       |
       v
Webhook Worker
       |
       +---- Success ---> delivered
       |
       +---- Failure ---> retry
```

The webhook payload is stored before delivery.

The worker sends the stored payload to the registered endpoint.

Failed deliveries can be retried up to three times.

Because delivery is at-least-once, receiving applications must make event processing idempotent.

---

# 8. Webhook Signature Verification

Webhook requests contain:

```http
X-Webhook-Signature: <signature>
```

The signature is generated using HMAC-SHA256 and the shared webhook secret.

The receiving application should:

1. Read the raw HTTP request body.
2. Calculate the HMAC-SHA256 signature using the shared secret.
3. Compare the calculated signature with `X-Webhook-Signature`.
4. Reject the request if the signatures do not match.
5. Process the event only after signature verification.

The signature must be calculated against the exact raw request body.

Do not parse and re-encode the JSON before calculating the signature.

Example:

```text
signature = HMAC-SHA256(raw_request_body, webhook_secret)
```

Use a timing-safe comparison when checking the signature.

---

# 9. Handling Duplicate Webhooks

Webhook delivery is at-least-once, so the same event can be delivered more than once.

Receiving applications should use:

```text
event_id
```

as the webhook event idempotency key.

For example, before processing a `payment.completed` event, the receiving application can check whether the `event_id` has already been processed.

If it has, the application should acknowledge the webhook without performing the payment operation again.

This prevents duplicate business operations when the gateway retries a delivery.

# Payment Flow

## STK

```text
Client Application
       |
       | POST /mpesa/stk
       v
BrifNet M-Pesa Gateway
       |
       | STK Push
       v
Customer Phone
       |
       | Payment
       v
Safaricom Daraja
       |
       | STK Callback
       v
BrifNet M-Pesa Gateway
       |
       | payment.completed
       v
Client Webhook Endpoint
```

The STK initiation response only confirms that the STK request was accepted for processing.

The `payment.completed` webhook is the completion notification.

## C2B

```text
Customer
    |
    | C2B Payment
    v
Safaricom Daraja
    |
    | C2B Callback
    v
BrifNet M-Pesa Gateway
    |
    | payment.completed
    v
Client Webhook Endpoint
```

For C2B, the gateway receives the account number from the M-Pesa `BillRefNumber` field and the provider transaction ID from `TransID`.

# Example Integration

## Step 1 — Initiate an STK Payment

```http
POST https://your-domain.com/wp-json/brifnet/v1/mpesa/stk
Content-Type: application/json
```

```json
{
  "reference": "ORDER-1001",
  "phone": "0729633304",
  "amount": 500
}
```

## Step 2 — Wait for Completion

Do not treat a successful STK initiation response as proof of payment.

Wait for:

```text
payment.completed
```

## Step 3 — Verify and Process the Webhook

Example:

```json
{
  "event_id": "evt-1001",
  "event": "payment.completed",
  "occurred_at": "2026-09-04T12:30:00+03:00",
  "data": {
    "reference": "ORDER-1001",
    "phone": "0729633304",
    "amount": 500,
    "channel": "STK",
    "provider_reference": "ws_CO_67890",
    "provider_transaction_id": "ABC123XYZ"
  }
}
```

The receiving application should:

1. Verify the HMAC signature.
2. Validate the payload.
3. Check `event_id` for duplicate processing.
4. Locate the corresponding payment/business record using `data.reference`.
5. Process the completed payment.
6. Return a successful HTTP response.

* `README.md`
* Source code

* Public WordPress directories

# Notes

The M-Pesa provider callbacks and the client-facing API are separate parts of the system.

Client applications normally use:

```text
POST /mpesa/stk
```

to initiate STK payments and subscribe to:

```text
payment.completed
```

to receive payment completion notifications.

The provider callback endpoints:

```text
POST /mpesa/callback
POST /mpesa/c2b
```

are used internally by the gateway to receive notifications from Safaricom Daraja.

Daraja callback URL registration is currently a manual configuration step.
